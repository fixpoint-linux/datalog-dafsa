Semantic vector search

Meaning-aware retrieval on top of the full-text index. The engine does not embed: it takes a pre-encoded 256-bit ITQ signature plus a pre-quantized int8 query vector, retrieves candidates with multi-index hashing (MIH) over ITQ bit-codes, and re-ranks by exact int8 cosine — all stored in-relation and snapshot-versioned like everything else. The embeddings themselves come from an encoder you run outside the engine and are ingested as ordinary relations.

Quickstart

No embedding model and no ggml ship in this repository. You produce the vectors with your own encoder, write them out as the relations below, and load them like any other facts; the engine supplies the retrieval tier on top. 

# 1. Encode the corpus OUTSIDE the engine (any bge-small-class model) and emit the
#    relations: __sig{0..15}__, __vec_q__, __itq_basis__.
$ <your-encoder> --db /tmp/db

# 2. Load each relation (18 loads) + one atomic publish.
$ ./dl -d /tmp/db load vec/__sig0__.csv --rel __sig0__   # ... __sig15__, __vec_q__
$ ./dl -d /tmp/db publish

# 3. Query it with a pre-encoded query (see "The CLI" below).
$ ./dl -d /tmp/db vsearch 'affordable GPU rental' --sig <64-hex> --ivec <768-hex> --k 10
$ ./dl -d /tmp/db vhybrid 'gpu rental' 'affordable GPU rental' --sig <64-hex> --ivec <768-hex>

How it works

Each entity is embedded (externally) and binarized to a 256-bit ITQ signature. The signature is split into m=16 bands; for band j the store keeps a fixed-arity relation __sig{j}__(band_u32, entity_sym_id) — a postings index from bit-substring to entity sym-id, the same shape as the full-text postings. 

__sig0__..__sig15__   (arity 2)  band_value -> entity_sym_id    MIH candidate postings
__vec_q__            (arity 3)  entity_sym_id, chunk_idx, packed_4x_int8_u32   re-rank vectors
__itq_basis__        (arity 3)  dim_i, dim_j, float32_bits_u32   ITQ encode matrix (pinned)

A query is encoded by the same external encoder, then for each band the engine enumerates the query’s substring variants within the pigeonhole budget ⌊r/m⌋, probes each via dl_prefix over __sig{j}__, unions the candidates across bands, filters to live entities, and re-ranks by exact integer int8 cosine. All reads are snapshot-versioned like any other relation, so dl_vector_search_version and dl search --version give you time-travelling semantic search for free.

The CLI

vsearch

Semantic vector search over the MIH postings + int8 re-rank.

dl [-d <dir>] vsearch '<query>' [--k N] [--radius R] [--version V]
                                  [--sig <hex64>] [--ivec <hex768>]

--version V queries as-of a published snapshot (0 = live). The query is always passed pre-encoded: --sig (8 u32 = 64 hex, the ITQ signature) and --ivec (96 u32 = 768 hex, the int8 vector).

vhybrid

Lexical ∩ semantic hybrid: intersect search results with vsearch candidates, then re-rank the intersection.

dl [-d <dir>] vhybrid '<terms>' '<query>' [--k N] [--radius R] [--version V]

search (full-text)

The symbolic half: AND-intersect tokenized terms over __postings__ and rank by co-occurrence. --version N queries as-of a snapshot.

dl [-d <dir>] search '<terms>' [--top N] [--version N]

Producing embeddings (external encoder)

Embedding is out of scope for this engine and out of tree. The former C++/ggml dl-embed sidecar, its ggml submodule and the git-lfs GGUF model are removed; what remains is the two-part contract any encoder must meet:

  1. Corpus. Emit the vector relations as CSVs and load them with dl load: __sig{0..15}__ (band → entity sym-id), __vec_q__ (entity sym-id, chunk, packed int8), __itq_basis__ (the ITQ encode matrix, pinned by snapshot). Band layout is MSB-first and must match the engine's read formula exactly — see the storage scope doc.
  2. Query. Produce the same 8-word signature + 96-word int8 vector for the query text and pass them as --sig/--ivec. Given a bare text query the CLI instead fork/execves a program named dl-embed (next to the dl binary, else ./dl-embed), calling dl-embed encode --db DIR QRY and reading one sig_hex ivec_hex stdout line. Nothing ships to fill that slot, so a bare text query fails until you install one.

Design

The full design of record lives in the design docs: datalog-dafsa-vector-search.md (MIH over ITQ, the integration seam, honest ceiling) and the int8-in-store note. In short: in-store MIH is competitive with HNSW at ~1e5–1e6 entities and wins the consolidation story — one identity space, one snapshot, one WAL, one crash-recovery story.
